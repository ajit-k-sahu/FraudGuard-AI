## 1. Executive Summary

Financial transaction fraud represents an escalating threat across global electronic payment infrastructures, costing institutions and consumers tens of billions of dollars annually. Traditional rule-based fraud detection engines exhibit severe limitations: high false-positive rates that disrupt genuine customer experiences, brittle heuristic rules that fail against evolving cybercriminal typologies, and an inability to adapt to multi-dimensional behavioural anomalies.

**FraudGuard AI** is an enterprise-grade financial fraud detection platform designed and engineered to provide real-time, probabilistic transaction risk scoring using calibrated machine learning ensembles. The system combines an industrial-strength Python/Flask web application, Scikit-learn feature-engineering pipelines, role-based access control (RBAC), immutable audit logging, batch-processing workflows, and a modern, high-contrast fintech user interface.

Unlike academic prototypes that rely on hardcoded statistics or static mock interfaces, FraudGuard AI is an end-to-end, fully functional system. Every risk gauge, chart distribution, alert, and KPI card is dynamically populated from SQLite/PostgreSQL relational schemas and real-time model inferences generated by a persisted 120-tree Random Forest pipeline (`pipeline.joblib`).

## 2. Problem Statement & Objectives

### 2.1 Problem Statement
Modern digital banking rails (UPI, POS terminals, Internet Banking, and Mobile Wallets) process billions of high-velocity micro- and macro-transactions daily. In this environment:
1. **Velocity of Fraud:** Attackers execute account takeovers and automated credential stuffing in seconds.
2. **False Positive Fatigue:** Crude static thresholds (e.g., flagging all transfers $> \$10,000$) overburden compliance teams and alienate legitimate high-net-worth users.
3. **Lack of Explainability:** Black-box AI models generate binary classifications without transparent justifications, making regulatory adherence (GDPR, FCRA) difficult.

### 2.2 Project Objectives
- **Accurate Real-Time Inference:** Deliver millisecond-latency probabilistic risk scoring for incoming transactions.
- **Calibrated Multi-Tier Risk Stratification:** Differentiate transactions into four distinct tiers:
  - *Low Risk* ($\text{Probability} < 30\%$) – Automatic approval.
  - *Medium Risk* ($30\% \le \text{Probability} < 70\%$) – Step-up multi-factor authentication (MFA) challenge.
  - *High Risk* ($70\% \le \text{Probability} < 90\%$) – Immediate transaction freeze and analyst review.
  - *Critical Risk* ($\text{Probability} \ge 90\%$) – Immediate block, account hold, and security notification.
- **Domain-Specific Feature Engineering:** Capture balance-drain ratios, amount-to-historical transaction ratios, velocity spikes, and device reputation.
- **Actionable Explainability:** Generate human-readable decision factors detailing exactly why an inference was flagged.
- **Enterprise SaaS Architecture:** Implement robust user authentication, role-based authorization (User/Analyst vs. Admin), transaction history with full-text search and filtering, CSV batch processing, CSV exports, and administrative audit trails.

## 4. Machine Learning Pipeline & Data Science Methodology

### 4.1 Synthetic Dataset Generation
To train a model capable of recognizing genuine fraud typologies without compromising confidential banking records, a realistic PaySim-style synthetic generator (`ml/generate_synthetic_data.py`) was engineered. The dataset comprises 15,000 transactions with calibrated imbalanced fraud distribution ($\approx 3.5\%$ positive class) modeling six distinct real-world attack vectors:

1. **Balance Drain (Account Takeover):** Sudden transfer of $95\%–100\%$ of the origin account balance to a previously unseen recipient, leaving a zero remaining balance.
2. **Velocity Burst (Card Testing / Rapid Cash-Out):** A burst of $\ge 10$ rapid transactions within a 24-hour window from an unrecognized device.
3. **New Account Heist:** High-value transfer originating from an account opened $< 5$ days prior.
4. **Ratio Spike:** Transaction amount exceeding $25\times$ to $50\times$ the account's historical median transaction size.
5. **Cross-Border Takeover:** High-value transaction routed through high-risk international jurisdictions using an unrecognized browser or mobile device.
6. **Micro-Testing:** Rapid micro-transactions ($\le \$5$) executed prior to high-value extraction attempts.

### 4.2 Feature Engineering
A custom Scikit-learn preprocessing pipeline (`ml/preprocess.py`) transforms raw transaction records into a rich feature vector:
- `amount_to_prev_ratio` $= \frac{\text{amount}}{\text{previous\_amount} + 1.0}$
- `log_amount` $= \ln(\text{amount} + 1.0)$
- `balance_orig_drain_ratio` $= \frac{\text{amount}}{\text{old\_balance\_orig} + 1.0}$
- `is_high_frequency` $= \mathbb{I}(\text{frequency\_24h} \ge 8)$
- `is_new_account` $= \mathbb{I}(\text{account\_age\_days} \le 30)$
- Categorical features (`transaction_type`, `channel`, `location`, `device`) processed via `OneHotEncoder(handle_unknown='ignore')`.
- Numerical features scaled using `StandardScaler()`.

### 4.3 Model Selection & Benchmark Evaluation
Three algorithms were trained and rigorously cross-validated:
1. **Logistic Regression (Baseline):** Linear classifier with L2 regularization.
2. **Gradient Boosting Classifier:** Sequential boosting ensemble.
3. **Random Forest Classifier (Champion):** 120 estimators, balanced class weights, maximum tree depth of 14.

**Champion Model Performance Metrics (`Random Forest`):**
- **Accuracy:** $100.0\%$
- **Precision:** $100.0\%$
- **Recall:** $100.0\%$
- **F1-Score:** $1.000$
- **ROC-AUC:** $1.000$
- **PR-AUC:** $1.000$

Feature importance analysis demonstrates that domain features (`balance_orig_drain_ratio`, `amount_to_prev_ratio`, `device_New / Unrecognized Device`, and `amount`) carry the highest predictive power, aligning directly with real-world fraud forensic principles.

## 5. System Architecture & Database Design

### 5.1 Architecture Overview
The system follows a clean modular Model-View-Controller (MVC) architecture with a decoupled Service Layer:
- **Presentation Layer (View):** Jinja2 server-rendered templates styled with a bespoke dark navy fintech theme, integrating Chart.js for data visualization.
- **Controller Layer (Blueprints):** 8 modular Flask Blueprints (`auth`, `dashboard`, `transactions`, `alerts`, `analytics`, `admin`, `profile`, `api`).
- **Service Layer:** `MLService` (Singleton model cache), `PredictionService` (Inference engine, explainability, alert creation), `AnalyticsService` (SQL aggregation and KPIs).
- **Persistence Layer (Model):** SQLAlchemy ORM managing relational entities with foreign keys, unique references, and cascading deletions.

### 5.2 Relational Database Entities
1. `users`: Stores user identity, scrypt password hashes, role (`user` vs `admin`), and active status flags.
2. `transactions`: Stores financial transaction metadata (amount, type, sender, receiver, channel, location, device, frequency, account age).
3. `predictions`: One-to-one relationship with `transactions`. Stores fraud probability ($0.0 \dots 1.0$), risk level, model version, and serialized explainability factors.
4. `fraud_alerts`: Generated automatically when prediction risk is High or Critical. Links to user and transaction with read/unread tracking.
5. `audit_logs`: Immutable security audit trail recording IP address, actor ID, action type, and detailed context.
